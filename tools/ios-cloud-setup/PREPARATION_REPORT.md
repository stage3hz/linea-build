# Подготовка Linea к облачной iOS-сборке

## Проверенный результат

`prepare-ios.mjs` подготовил отдельную копию исходников Linea 0.5.0. На Linux успешно выполнены Expo config и `expo prebuild --platform ios --no-install`. После применения `--app-version 0.5.1` повторная генерация также завершилась с кодом 0; `CFBundleShortVersionString` стал `0.5.1`.

Скрипт инициализации не запускает Expo, установку зависимостей, сборку, вход в аккаунты или подпись. Эти проверки выполнялись отдельно в `/tmp/linea-ios-cloud-check/mobile`. В основной проверочной копии отсутствовали `owner` и `extra.eas.projectId`; чужие или выдуманные идентификаторы в неё не добавлялись. Синтетические идентификаторы использовались только в одноразовых тестовых каталогах.

**CocoaPods, компиляция Xcode/Swift, облачная EAS-сборка, создание IPA и установка на iPhone в эту проверку не входили.** Результат подтверждает генерацию конфигурации; работоспособность iOS-приложения ещё должна пройти соответствующие сборку и испытания.

## Контракт helper

```sh
node prepare-ios.mjs /path/to/mobile \
  [--project-id UUID] \
  [--owner EXPO_NAME] \
  [--bundle-id IOS_BUNDLE_ID] \
  [--app-version MAJOR.MINOR.PATCH]
```

Все параметры необязательны, кроме пути. Передаются только публичные настройки. Владение Expo-проектом или Apple bundle identifier скрипт не проверяет. `--app-version` принимает три числовые части без ведущих нулей и prerelease-суффиксов. Он меняет только `expo.version`; `package.json`, lockfile, UI, Android versionCode и iOS buildNumber остаются задачей владельца следующего релиза.

Перед первой записью обязательны точные SHA-256:

| Файл исходного mobile 0.5.0 | SHA-256 |
| --- | --- |
| `app.config.js` | `0c514d669eba235570ca5d62a598db6da4c1d8ab6819f6b0f8657d530e0b20d3` |
| `eas.json` | `067a38734aa7fc0e4aaed23d7525071b82a2857f0f26c5cf72d8dd6f0a36afff` |

Helper добавляет `ios.useFrameworks: 'static'` к существующему `expo-build-properties`, конфигурационный guard и недостающие Android-блокировки разрешений. Перед записью сохраняет неизменённые `app.config.original.js` и `eas.original.json` в `.linea-ios-cloud-setup/`; туда же копирует guard. Для подключения guard эта папка должна оставаться в загружаемой пользовательской копии проекта.

Публичные настройки записываются JSON-заголовком в `app.config.js`. При следующем запуске helper восстанавливает ожидаемый текст из проверенного оригинала и сравнивает весь файл. Изменения вне helper, испорченные backups или изменённый guard приводят к отказу с сохранением существующих файлов. Полный повтор без изменений не переписывает файл. `eas.json` никогда не перезаписывается: после первоначальной проверки его последующие настройки сохраняются. Запись app config использует временный файл, повторную проверку текущего текста и rename; собственная lock-запись исключает одновременные запуски helper.

Для следующего релиза сначала применяют helper к копии с исходными `app.config.js` и `eas.json`, передав `--app-version 0.5.1`. `package.json.version` может быть исходным `0.5.0` либо текущей/запрашиваемой версией из helper. При последующем добавлении настоящих `--owner`/`--project-id` версия сохраняется. Произвольный уже вручную изменённый app config helper не перезаписывает.

## Почему включены статические фреймворки

Локальная официальная документация libsignal из tag `v0.106.0`, `/tmp/linea-libsignal-01060/swift/README.md`, содержит требование: “Make sure you are using `use_frameworks!` in your Podfile.” SHA-256 прочитанных 4 628 байт: `727d2db250cd87fdc4ebb691753d040f02e29ca48cd6e5c69b3beb126411ee8e`. Соответствующий upstream-путь: <https://github.com/signalapp/libsignal/blob/v0.106.0/swift/README.md>. Приведённая проверка опиралась на эти локальные первичные bytes; повторное сетевое получение не выполнялось.

В исходной app config была только Android-часть `expo-build-properties`. Установленный шаблон Expo читает `ios.useFrameworks` из `Podfile.properties.json` и передаёт его в `use_frameworks!`. После подготовки в generated Podfile присутствуют статическая настройка и `LibSignalClient` tag `v0.106.0`. Это устранение расхождения с документированным требованием; воспроизведённой ошибки Swift-компилятора здесь нет.

## Проверки разрешений и изоляции

В Android blockedPermissions добавлены/сохранены следующие обязательные ограничения (каждое с префиксом `android.permission.`):

`ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION`, `ACCESS_BACKGROUND_LOCATION`, `ACCESS_MEDIA_LOCATION`, `SYSTEM_ALERT_WINDOW`, `QUERY_ALL_PACKAGES`, `PACKAGE_USAGE_STATS`, `MANAGE_EXTERNAL_STORAGE`, `READ_CONTACTS`, `WRITE_CONTACTS`, `READ_CALENDAR`, `WRITE_CALENDAR`.

Сохранены также прежние `RECORD_AUDIO`, `CAMERA`, `WRITE_EXTERNAL_STORAGE`, `READ_MEDIA_AUDIO`; всего итоговый список содержит 16 различных разрешений. Изменения действуют только при последующей сборке этой подготовленной копии. **Опубликованный APK 0.5.0 не изменён; присутствовавшее в нём `SYSTEM_ALERT_WINDOW` этим kit не удаляется.** Android manifest из новой конфигурации в рамках этой задачи не собирался.

`withLocalPrivacy.cjs` проверяет исходную конфигурацию, а затем использует установленный Expo `withFinalizedMod`. По исходному коду Expo этот этап выполняется после остальных mods. Guard читает сформированные Podfile/properties, Info.plist и entitlements и останавливает prebuild при:

- `NSLocation*`, фоновом режиме `location` или `LSApplicationQueriesSchemes`;
- `UIFileSharingEnabled` или `LSSupportsOpeningDocumentsInPlace`, если значение не является строго boolean `false`; отсутствие ключа разрешено, значения `true`, `1`, `"YES"` и `null` отклоняются;
- явно добавленных app groups или `keychain-access-groups`;
- отсутствии требуемых Android-блокировок, статических фреймворков или LibSignalClient-интеграции;
- непредусмотренной структуре/размере проверяемых файлов.

В успешном generated проекте фоновые режимы содержат только `audio`, entitlements пусты; геолокационных ключей и запросов к перечню установленных приложений нет. Системный выбор фото и описания доступа к пользовательским медиа сохранены. Guard не добавляет runtime-доступ к clipboard, геолокации, общей памяти или другим приложениям.

Проверка относится к конфигурации CNG/prebuild. Это не аудит всего runtime-кода и зависимостей, не исследование уже подписанного IPA и не гарантия для произвольного Xcode-проекта, собранного в обход prebuild. Обычная собственная область Keychain приложения и автоматически сформированные подписью entitlement-поля здесь не анализировались.

Первый прогон helper дал 12/13: отсутствующая `package.json.version` ошибочно принималась, потому что `undefined` присутствовал среди необязательных сравниваемых версий. После явной проверки строкового типа тот же сценарий получил отказ, весь набор — 13/13. Этот дефект относился только к новому helper. После добавления семи Android-блокировок и строгой проверки обоих Documents-ключей те же наборы получили 13/13 и 23/23. Детальные результаты и контрольные суммы находятся в `VERIFICATION.json` и `evidence/`.

Выполненная подготовка не создаёт платное Apple-членство, сертификат, provisioning profile, регистрацию устройства или Expo-проект. Для реальной облачной сборки пользователь должен отдельно предоставить/создать собственный EAS-проект, доступный bundle identifier и необходимые Apple-ресурсы. Текущий `preview` остаётся профилем для физического устройства с внутренним распространением; его конфигурация не менялась.
