**Дополнение 0.5.0:** актуальный состав — [RELEASE_0.5.md](RELEASE_0.5.md). Следующая матрица — исторический срез 0.3, а не текущий список новых функций.

Новый редактор фото реализован отдельной итерацией; его фактические режимы, ограничения и проверки находятся в [PHOTO_FEATURES.md](PHOTO_FEATURES.md) и [TEST_REPORT.md](TEST_REPORT.md). Остальные перечисленные отсутствующие функции этим обновлением не добавлены.

Дата сверки: **28 октября 2026 года**. Базовая версия Linea для этой матрицы — **0.3.0, до добавления нового фоторедактора**. Документ фиксирует требования и разницу в возможностях, а не объявляет перечисленные функции реализованными.

**Полное соответствие Telegram в текущем приложении не достигнуто. Я не могу это подтвердить.** В исходниках есть основа личной переписки, собственная авторизация, музыка и нативное сквозное шифрование; значительная часть функций Telegram отсутствует. Новые функции обработки фото должны подтверждаться отдельным отчётом следующей версии, а не засчитываться задним числом в 0.3.0. Основания: [контракт API][L1], [типы клиента][L2], [серверные маршруты][L3], [отчёт 0.3.0][L9].

## Как читать матрицу

- **Есть в коде** — найдены соответствующие API и клиентская реализация; это не заменяет проверку на настоящих Android/iPhone.
- **Частично** — есть часть сценария, но отсутствуют перечисленные составляющие.
- **Нет в 0.3.0** — сценарий не реализован в просмотренных API, модели данных и клиентских экранах.
- **Отличается по требованиям** — поведение Linea намеренно иное, например вход без номера телефона.

Проверены основные пользовательские и платформенные группы возможностей по официальным API, FAQ и публикациям Telegram. Это рабочая матрица, а не утверждение об исчерпывающем перечислении каждого поля API, каждого варианта интерфейса и каждого ограничения аккаунта. Telegram развивается, а его FAQ прямо предупреждает о возможном отставании текста; поэтому для новых возможностей использованы также актуальные страницы API и публикации 2025–2026 годов. Доступность отдельных функций Telegram зависит от типа чата, клиента и подписки. [T1][T2][T12]

## 4. Что означает выбранное шифрование для соответствия

У Telegram облачные чаты и Secret Chats различаются: облачная история синхронизируется через платформу, тогда как Secret Chats используют E2EE и привязаны к исходным устройствам. Нельзя описывать все сообщения Telegram как сквозно зашифрованные по умолчанию. В текущей Linea новые личные сообщения и вложения шифруются на устройствах, а сервер хранит шифротекст; потерянные приватные ключи не восстанавливаются по паролю или короткому слову. [T1][L8][L11]

**Следующие пункты — инженерные следствия выбранной архитектуры, а не уже выполненные функции:**

1. Поиск по приватному содержимому нужно выполнять на доверенном клиенте или через отдельно спроектированный безопасный механизм. Передача всей открытой переписки серверу ради поиска изменила бы заявленную модель.
2. Новый телефон должен получать историю и ключи через явно разработанный перенос либо зашифрованную резервную копию. Простого входа по нику недостаточно для истории, которую телефон не мог расшифровать.
3. Группы требуют правил добавления/удаления участников, обновления ключей и доставки на устройства. Нельзя доказать пригодность для больших групп одними тестами личного чата.
4. У публичного канала, закрытой группы и личного чата разные аудитории. Для каждого типа нужно отдельно определить, кто имеет доступ к содержимому и что именно защищает шифрование.
5. Бот или облачный AI, которому сознательно передали открытый текст/фото, становится дополнительным получателем этих данных. Такое действие должно быть отдельным понятным выбором.
6. Исчезновение в интерфейсе, удаление серверной копии и гарантированное уничтожение всех уже полученных копий — разные требования. Последнее нельзя обещать только на основании таймера.

С групповой связью Telegram также важно различать режимы: официальная документация отдельно описывает E2EE-конференции и видеочаты/трансляции групп и каналов. Наличие E2EE-конференций не следует автоматически переносить на каждый режим трансляции. [T32]

| Шифрование | Можно сохранять выбранную модель E2EE, включая будущий перенос истории. [L8] | Следует модели соответствующего типа чата Telegram; обёртка не превращает облачные чаты в Secret Chats. [T1][T5] |
| Собственные функции фото/музыки | Добавляются к нашему процессу отправки и собственной библиотеке. | Могут расширять клиент при соблюдении API terms; нужен совместимый формат отправки для других клиентов. [T6] |
| Условия платформы | Собственные серверные правила и ответственность за работу продукта. | Нужен собственный `api_id`, указание использования Telegram API и соблюдение условий. Клиент с каналами должен поддерживать официальные sponsored messages. Обещать их произвольное отключение нельзя. [T6] |

**Решение этой итерации:** архитектура не переключается на TDLib. Продолжается собственная Linea, поскольку это согласуется с уже выбранными аккаунтами без номера и собственным сервером. Вариант TDLib рассмотрен как отдельная возможная смена продукта, а не скрытая замена текущей разработки. Никаких Telegram API credentials, аккаунтов или платных сервисов этим документом не создаётся.

## 6. Новые требования к фото: отдельный пункт приёмки

Источник этого раздела — сообщение пользователя: все возможности Telegram плюс обработка фото перед отправкой. Для 0.3.0 ни один перечисленный ниже режим не засчитан как готовый: старый `choosePhoto` передаёт выбранный файл в шифрование, без собственного фоторедактора. [L4][L11]

| Требование | Проверяемый результат следующей реализации |
| --- | --- |
| Фото без фона | Результат с прозрачностью, видимый предпросмотр и возможность отмены. |
| Фото с белым фоном | Белая подложка под выделенным объектом; отдельный просмотр результата. |
| Апскейлер | Явный масштаб, ограничение размера и точное обозначение способа увеличения. Обычный resize не выдаётся за восстановление неизвестных деталей моделью. |
| Удаление объектов | Выбор области, обработка, сравнение до/после и отмена; не обещается точная реконструкция того, чего не было видно на исходнике. |
| Документ Ч/Б без теней | Обработка освещения и контраста с сохранением читаемости; результат проверяется на фактических снимках документов. |
| Цветной документ | Коррекция освещения с сохранением цветного содержимого и проверкой читаемости. |
| Автоматический PNG | В цепочку шифрования поступает результат с фактическим PNG-содержимым и согласованным именем/MIME. Простого переименования файла недостаточно. |
| Отсутствие пользовательских метаданных | Проверяется полученный файл, а не только скрытие EXIF в интерфейсе. Формат всё равно содержит служебные данные, необходимые для декодирования изображения. Формат PNG определён в [спецификации W3C](https://www.w3.org/TR/png-3/). |
| Приватность обработки | Ясно обозначить локальную и внешнюю обработку; не отправлять оригинал внешнему обработчику под обещанием, что его видят только участники переписки. |

Реализация и статус этих режимов должны сопровождаться отдельными тестами и отчётом. Этот документ сам по себе ничего из перечисленного не реализует.

## 7. Порядок работ и критерии готовности

Это предложенный порядок по зависимостям, без выдуманной оценки сроков или процента готовности.

| Этап | Содержание | Условие перехода |
| --- | --- | --- |
| 1 | Новый фоторедактор и неизменность безопасной отправки | Обработка результата, формат и метаданные проверены; есть отмена/ошибки; шифрование получает именно подготовленный файл. |
| 2 | Надёжная основа Android/iPhone | Настоящие сборки и испытания двух устройств, корректное хранение ключей, закрытые push, восстановление после сбоев и описанный перенос истории. |
| 3 | Полноценная личная переписка | Ответ/редактирование/удаление/пересылка/реакции, поиск, папки, «Избранное», голосовые/альбомы, черновики и планирование имеют серверные и клиентские сценарии. |
| 4 | Группы, каналы и управление доступом | Миграции, роли, приглашения, темы, модерация и модель шифрования проходят проверки изоляции и смены состава. |
| 5 | Звонки и публичные медиа | Личные/групповые вызовы, трансляции и истории проверены в фоне, при смене сети и на реальных телефонах; нагрузка измерена для согласованной аудитории. |
| 6 | Боты, Mini Apps и расширенные сервисы | Стабильный API и разрешения, совместимость клиентских версий, наблюдаемость, выбранные бизнес-/платёжные/AI-функции. |
| 7 | Проверка всей согласованной матрицы перед выпуском | Для каждого принятого пункта есть демонстрируемый пользовательский сценарий, проверка серверной логики, сценарии ошибок и подтверждение поддержанных платформ. |

Нет оснований называть 0.3.0 полным аналогом Telegram, масштабируемым до его аудитории либо готовым к публичному выпуску только по наличию APK. Нативные и автоматические результаты, а также непрошедшие пороги дополнительной проверки качества, зафиксированы в [TEST_REPORT][L9], [NATIVE_TEST_REPORT][L14] и [QUALITY_REPORT][L15].
