# Бессрочная Platina в 0.5.1

В серверной версии 0.5.1 добавлена настоящая выдача Platina без даты окончания. Она хранится как `expires_at = NULL` у административной записи и привязана к неизменяемому UUID аккаунта. Дата «2099», бесконечное число или клиентский флаг для этого не используются.

Бессрочность означает отсутствие автоматического истечения. Администратор сервера по-прежнему может отозвать право. Смена публичного имени, перезапуск сервера и штатное восстановление пароля его не снимают. Если освобождённое имя займёт другой аккаунт, Platina останется у исходного UUID.

Это право на возможности Platina, реализованные в приложении: повторные смены публичного имени и статичный статусный эмодзи. Оно не создаёт роль системного администратора, доступ к чужим сообщениям, ключам сквозного шифрования, аккаунтам или серверу. Общая система ролей и платежи в эту доработку не входят.

**При подготовке этой версии ни одному реальному аккаунту право не выдавалось.** Все проверки выполнялись на синтетических аккаунтах во временных базах. Для реальной выдачи сначала нужен созданный аккаунт и его текущее публичное имя на нужном сервере.

## Перед обновлением: резервная копия

Сервер автоматически переводит SQLite со схемы 4 на схему 5 при первом обычном открытии базы версией 0.5.1. Это происходит при запуске API, а также при административной выдаче или отзыве. Команда `lookup` только читает уже существующую базу схемы 4 или 5 и миграцию не запускает.

**Сделайте резервную копию до первого запуска API 0.5.1 или изменяющей команды 0.5.1 на существующих данных.** Для развертывания из [DEPLOY_FROM_IPHONE.md](DEPLOY_FROM_IPHONE.md), где проект находится в `/opt/linea`:

```bash
cd /opt/linea
bash deploy/backup.sh /var/backups/linea
```

Штатный скрипт ненадолго останавливает API, архивирует весь каталог `/data` вместе с SQLite, WAL и загрузками, затем запускает API снова. Сохраните полученный архив отдельно от VPS и проверьте возможность восстановления. Простое копирование одного работающего `linea.sqlite` не заменяет эту процедуру.

Миграция заменяет только таблицу `platina_entitlements` внутри транзакции: сохраняются UUID аккаунта и выдачи, источник, время выдачи, прежний конечный срок и время отзыва. История `platina_audit` не перестраивается. Поле срока становится nullable, остальные права не выдаются автоматически. Повторное открытие схемы 5 не переиздаёт Platina.

Сервер 0.5.0 откажется открывать схему 5. Для отката к нему понадобится восстановление согласованной резервной копии схемы 4; вручную понижать `PRAGMA user_version` нельзя.

## Выдача через доверенную серверную команду

Команды выполняет оператор с доступом к серверу. Удалённого HTTP-метода для выдачи, клиентской кнопки администратора и обхода проверки UUID нет. Не передавайте для этого пароль пользователя, секретные слова или ключи шифрования.

После установки серверного кода 0.5.1 найдите аккаунт по **текущему публичному имени без `@`**. В примере замените `current_username` фактическим именем:

```bash
cd /opt/linea
docker compose --env-file deploy/.env -f deploy/compose.production.yml exec -T api \
  node src/platina-admin.js lookup \
  --data-dir /data \
  --username current_username
```

Результат содержит только UUID, найденное публичное имя и статус Platina:

```json
{
  "accountId": "UUID найденного аккаунта",
  "username": "current_username",
  "platina": { "active": false, "expiresAt": null }
}
```

Регистр и внешние пробелы нормализуются так же, как в приложении. Старый приватный логин не используется как запасной ключ поиска после смены публичного имени. Несуществующее имя приводит к ошибке и ничего не выдаёт. Команда также не создаёт отсутствующую базу данных.

Сверьте найденный аккаунт. Затем замените `ACCOUNT_UUID` ровно на `accountId` из результата:

```bash
docker compose --env-file deploy/.env -f deploy/compose.production.yml exec -T api \
  node src/platina-admin.js grant-permanent \
  --data-dir /data \
  --user-id ACCOUNT_UUID \
  --reason 'Бессрочная Platina по решению владельца сервера'
```

Успешный результат:

```json
{
  "accountId": "UUID найденного аккаунта",
  "platina": { "active": true, "expiresAt": null, "permanent": true }
}
```

`grant-permanent` принимает только `--data-dir`, `--user-id` и `--reason`. Имя пользователя вместо UUID, `--username`, `--expires-at`, `--permanent` и неизвестные параметры отвергаются. Причина обязательна, не длиннее 500 символов и без управляющих символов. Если имя изменится между поиском и выдачей, уже найденный UUID продолжит указывать на тот же аккаунт.

Для запуска без Docker используйте ту же команду из корня исходников, заменив путь к данным существующим каталогом:

```bash
node server/src/platina-admin.js lookup --data-dir /absolute/data-directory --username current_username
node server/src/platina-admin.js grant-permanent --data-dir /absolute/data-directory --user-id ACCOUNT_UUID --reason 'Бессрочная Platina'
```

Каждая успешная выдача создаёт новый `grant_id`, атомарно записывает текущую выдачу и строку audit с `action = 'grant'`, `expires_at = NULL` и указанной причиной. Повторная команда выдачи — новая административная запись. Прежняя команда `grant --expires-at <UTC-ISO>` остаётся доступна для конечного срока; последняя явная выдача заменяет текущий вид права. Поэтому её не следует использовать для проверки уже выданной бессрочной Platina: для проверки служит `lookup`.

## Отзыв

```bash
docker compose --env-file deploy/.env -f deploy/compose.production.yml exec -T api \
  node src/platina-admin.js revoke \
  --data-dir /data \
  --user-id ACCOUNT_UUID \
  --reason 'Отзыв Platina по решению владельца сервера'
```

Отзыв оставляет историю и записывает `revoked_at`. Повторный отзыв не добавляет дублирующую строку audit. После отзыва сервер запрещает новые действия, требующие Platina, и перестаёт публиковать статусный эмодзи. Для ранее бессрочной выдачи приватный статус будет `{ "active": false, "expiresAt": null, "permanent": true }`: вид выдачи известен, но право не активно.

CLI не рассылает отдельное событие WebSocket подключённым клиентам. Актуальное право применяется сервером при каждом следующем запросе; отображение ранее загруженного профиля обновится после нового запроса профиля или повторного входа в приложение.

## Контракт API и отображения

| Состояние | Поле `platina` в `/me/username` |
|---|---|
| Выдачи нет или сохранённая запись недопустима | `{ active: false, expiresAt: null }` |
| Обычная активная выдача | `{ active: true, expiresAt: "UTC ISO дата" }` |
| Обычная истёкшая или отозванная выдача | `{ active: false, expiresAt: "UTC ISO дата" }` |
| Активная бессрочная выдача | `{ active: true, expiresAt: null, permanent: true }` |
| Бессрочная выдача отозвана или её начало ещё не наступило | `{ active: false, expiresAt: null, permanent: true }` |

Старые ответы без бессрочной выдачи сохраняют прежнюю форму: дополнительного `permanent: false` нет. Одно лишь `expiresAt: null` не доказывает наличие Platina. Сервер учитывает административный источник, допустимое время выдачи, начало действия и отсутствие отзыва.

У публичного пользователя `statusEmojiPermanent: true` появляется только одновременно с активной бессрочной Platina и допустимым выбранным эмодзи. Тогда `statusEmojiExpiresAt: null`. Если право отозвано, выдача недопустима либо эмодзи не выбран, публичный признак отсутствует и эмодзи скрыт. Обычный эмодзи по конечной выдаче по-прежнему содержит только конечный `statusEmojiExpiresAt`.

Клиентские запросы не могут записать `permanent`, `expiresAt`, `platina` или `statusEmojiPermanent` в право аккаунта. Управление профилем принимает только свои разрешённые поля; административный модуль не установлен как HTTP-маршрут.

Для отображения надписи «Бессрочно» и нового публичного признака нужен собранный клиент с изменениями 0.5.1. Этот серверный отчёт не подтверждает создание нового APK или IPA. Ранее собранный APK 0.5 остаётся отдельной исторической сборкой.

## Проверки

Сначала новые положительные сценарии запускались на старой реализации: **17 тестов прошли, 7 завершились ожидаемой ошибкой** из-за отсутствия permanent-поведения, CLI и схемы 5. После реализации целевой набор — **24/24 PASS** без пропусков. [Лог RED](evidence-v051/server-platina-red.txt), [лог GREEN](evidence-v051/server-platina-green.txt).

Полный серверный набор после изменения схемы — **93/93 PASS**, без ошибок и пропусков, за 242,7 секунды на Node.js 24.22.1. Он включает прежние сценарии авторизации, восстановления, HTTP/WebSocket, E2EE relay, AI и профиля. [Полный лог](evidence-v051/server-full.txt), [сводка и SHA-256 исходников](evidence-v051/server-validation.json). Независимый статический обзор изменённых серверных файлов не выявил блокирующих замечаний; отдельная сборка APK/IPA в этот прогон не входила.

Проверено:

- Настоящая миграция SQLite с прежним `expires_at NOT NULL`, конечными и отозванными выдачами, audit, пользователями, сессиями и незавершённым восстановлением; повторное открытие без изменений данных.
- `lookup` на схеме 4 без миграции и без выдачи прав; реальные отдельные процессы CLI для поиска, выдачи и отзыва.
- Активность бессрочной выдачи в 9999 году и на максимальной поддерживаемой границе времени JavaScript; начало действия и отзыв продолжают учитываться.
- Отказ для недопустимых или неадминистративных записей, неверных UUID, отсутствующих аккаунтов, причин, сроков и клиентских флагов.
- Переходы конечная → бессрочная → отозванная → бессрочная → конечная с корректной историей и публичными признаками.
- Реальный HTTP-сценарий: переименование, перезапуск API, восстановление пароля с ожиданием, вход заново, сохранение UUID/выдачи/audit, занятие прежнего публичного имени другим аккаунтом без передачи прав, затем отзыв.

Первый запуск в ограниченной песочнице дополнительно столкнулся с блокировкой Node subprocess. Его [отдельный диагностический лог](evidence-v051/server-platina-red-sandbox.txt) не используется как подтверждение работы CLI. Указанные RED/GREEN прогоны выполнены с разрешённым запуском локальных дочерних процессов, на временных синтетических базах.
