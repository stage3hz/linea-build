## Авторизованная область работы

Владелец показал рабочий VPS RUVDS: Ubuntu 24.04, 2 CPU, 4 GB RAM,
50 GB диска; в его терминале hostname `ruvds-k3pfq`. Пользователь с iPhone
может выполнять команды в своём SSH-клиенте. Этот сервер и прежний рабочий адрес
`141.133.194.51` не менять. Порты 80/443/3478/40000 уже используются, есть Docker
сети. Отдельный стенд или новая явно согласованная область работы необходимы до
любого размещения резервного транспорта. Текущая авторизация покрывает код ветки
и проверки; она не разрешает вмешательство в действующий API.

Работать только в `transport-b-integration`; не объединять Draft PR №1,
не менять `main`, `auto-connect-a`, `ipa-output`, подпись приложений, серверную
авторизацию и шифрование. Не делать force push. За время задачи защищённые ветки
менялись извне; это не разрешение откатывать или перезаписывать их.

## Доступ и прежняя попытка Codex CLI

Предыдущая среда Codex может обращаться к HTTP(S), но исходящий TCP/SSH в ней
не настроен. Подключение не дошло до SSH-аутентификации; сообщения
`Connection refused` также получены для контрольных SSH endpoints GitHub.
Из этого нельзя заключать, что SSH на VPS сломан. Владелец установил временный
публичный ключ; его срок истекает 17 ноября 2026, 18:00 UTC. Приватный ключ
был создан только в предыдущей среде, затем удалён после уточнения назначения VPS;
им ни разу не удалось авторизоваться. Никаких удалённых команд или
развёртывания из предыдущей среды не выполнено. Сам владелец по прежним командам
добавил временный публичный ключ, запустил SSH и установил Node/npm/Codex.
Не удалять эти пакеты вслепую: состояние и зависимости существующих служб неизвестны.
Не сооружать обратные shell/SSH-туннели для обхода сетевых ограничений.

Codex CLI на самом VPS выполняет команды локально. Его вход в ChatGPT отдельный
от Яндекс-входа. Для headless-машины официальный вариант —
`codex login --device-auth`: владелец открывает показанную официальную страницу
на телефоне и вводит код там. Доступность зависит от его тарифа и настроек
device-code login в аккаунте/организации. Не просить пароль, код или API key в чате.
Фактический результат этого пути: официальный установщик вернул HTTP 403,
установка через npm удалась (`codex-cli 0.169.0`), но `codex login --device-auth`
тоже вернул 403 до выдачи кода. Авторизации/запроса к модели нет. Не предлагать
повторную установку как исправление входа или обход ограничений доступа сервиса.

## Следующие технические действия

1. На отдельном, разрешённом для испытаний сервере подготовить приватный стенд
   и безопасный интерактивный вход владельца на
   официальной странице Яндекса. У upstream нет Telemost CLI QR/device/OAuth login
   (CLI `--login` существует только у Blink). Не запрашивать cookies/пароли в чате
   или GitHub. Сессию хранить только в приватном файле на стенде, вне репозитория.
   Общего браузера и перенесённой сессии в предыдущей среде не было.
2. Сначала доказать одну реальную пару Creator ↔ Joiner без публичного bootstrap.
   Записать безопасные счётчики успехов/отказов, не комнатные ссылки или токены.
   Не выдавать локальный mock или успешный start за рабочий транспорт.
3. Доказать сетевую изоляцию до публикации. Один только `--upstream-socks` не
   является границей. Creator и loopback egress должны видеть один network namespace
   либо корректный приватный relay; перенос только Creator ломает 127.0.0.1 gateway.
   Для разделения разрешений нужны отдельные UID и проверенная политика выхода:
   gateway — canonical API TCP/443, Creator — проверенный signalling/ICE, без
   произвольного прямого выхода. Учесть динамические SFU/TURN и общие CDN IP.
4. Проверить реальный SOCKS ATYP: текущий API-only egress разрешает hostname,
   отклоняет IP literal. Go сохраняет тип адреса CFNetwork; текущий native fixture
   принимает оба, поэтому он не доказывает, какой тип пришлёт физический iPhone.
   Не расширять allowlist вслепую. Проверить неверный host/port, UDP, private/metadata
   адреса и отключённый gateway: обходного выхода быть не должно.
5. После приватного доказательства подключать allocator/bootstrap на отдельном
   принадлежащем владельцу HTTPS ingress с прежними auth/device proof. Публично
   не выставлять общий SOCKS, VNC/CDP или незащищённый Creator.
6. Подготовить настроенную экспериментальную iOS-сборку и испытать на физическом
   телефоне: холодный запуск с недоступным direct, двусторонние сообщения,
   смена сети, отмена, direct return, прежние аккаунт/ключи/очередь без дублей.
   На реальной ограниченной сети проверить отдельно. Не обещать универсального
   обхода или готовности к сроку до этого результата.
