# Редактор фото перед отправкой — интерфейс и границы проверки

Дата: 28 октября 2026 года. Этот отчёт относится к интерфейсу и управлению временными результатами. Нативные алгоритмы, PNG-проверка и окончательная сборка проверяются отдельно.

## Поведение

`ChatScreen` открывает `PhotoEditor` после выбора изображения из галереи. Фото, выбранное через файловый диалог, также попадает в редактор по MIME или расширению. Установлены `quality: 1` и `exif: false` в picker; последнее само по себе не считается доказательством удаления EXIF из байтов. Окончательная очистка принадлежит общему PNG pipeline и проверке перед зашифрованной загрузкой.

Первый предпросмотр — обычный PNG с сохранением размеров в допустимых пределах. До нажатия **«Добавить PNG к сообщению»** редактор не вызывает загрузку вложения. После добавления фото остаётся вложением в черновике; отправку сообщения пользователь подтверждает обычной кнопкой чата.

Режимы интерфейса:

- исходник и готовый результат, отображение прозрачности на шахматном фоне;
- сохранение, удаление либо замена фона белым;
- чёрно-белый и цветной документ с выравниванием освещения;
- увеличение ×2 с явной подписью **«бикубическое»** и пояснением, что интерполяция не восстанавливает утраченные детали;
- выделение небольших объектов кистью, три размера кисти, отмена последнего мазка и сброс маски;
- применение, повторная обработка, сброс настроек и подтверждение готового PNG.

Документ и удаление фона взаимоисключающие: выбор одного режима сбрасывает другой. Это соответствует контракту native renderer. Удаление объектов честно описывается как заполнение окружающими цветами с возможным размытием текстуры, а не генеративная дорисовка.

## Размер и согласие

UI показывает исходные, промежуточные и предварительные итоговые размеры. Формула совпадает с согласованным native-контрактом: plain до 16 MP, эффекты до 4 MP, ×2 — база до 2 MP и результат до 8 MP. Размеры округляются вниз с сохранением пропорций.

Уменьшение требует отдельного согласия. Флажок доступен всегда: даже фото в пределах лимита пикселей может превратиться в PNG больше 20 МиБ. Текст объясняет возможность дополнительного уменьшения для соблюдения лимита файла; окончательные размеры берутся из реального результата обработки. Без согласия UI не запускает заведомо требующий уменьшения режим.

## Временные файлы и асинхронные операции

`PreviewSession` владеет только созданными PNG; исходник пользователя ему не передаётся для удаления. Изменение настроек делает прежний результат непригодным к отправке. Результат рендера, завершившегося после закрытия редактора или изменения настроек, освобождается.

На время загрузки результат удерживается отдельной ссылкой (`lease`): закрытие экрана или появление нового результата не удаляет файл, который ещё читает uploader. Освобождение идемпотентно. Ошибка загрузки оставляет актуальный предпросмотр для повторной попытки. Ошибки рендера отображаются в редакторе; исходник не отправляется в качестве скрытого fallback.

Результат системного picker связан с аккаунтом и чатом, из которых он открывался. Если контекст изменился за время выбора, поздний результат игнорируется; сохранённый редактор не показывается для другого чата. Это проверено обзором асинхронных переходов в коде, а не испытанием системного picker на телефоне.

Отмена разрешена во время подготовки/рендера; логическая отмена не утверждается остановкой native вычисления. Его поздний результат удаляется. На время уже подтверждённой загрузки кнопка закрытия блокируется. При внешнем unmount uploader сохраняет lease до своего завершения.

## Кисть

Координаты нормализованы относительно ориентированного изображения внутри `resizeMode="contain"`. Поля вокруг фотографии не попадают в маску. Радиус — доля меньшей стороны изображения. Между точками на экране показаны соединённые сегменты; текущий мазок завершается перед применением.

UI ограничивает маску 64 мазками и 1024 сохранёнными точками, не создавая неограниченное количество overlay views. Native renderer дополнительно проверяет контракт и суммарную площадь маски. Экраны сравнения, параметры и отправка блокируются во время активного мазка или обработки.

## Фактические проверки

Команда:

```sh
cd mobile
node --test --test-isolation=none test/photo-editor.test.mjs
```

Набор содержит 10 поведенческих проверок: соответствие координат изображению для двух пропорций, отбрасывание полей и нечисловых координат, сохранение разрешения plain PNG, явный прогноз уменьшения для фильтров и ×2, изображения из файлового диалога, плотность/предел выборки кисти, устаревший результат, закрытие во время рендера, удержание файла для upload и однократное освобождение при замене/закрытии.

Последний прогон: **10/10 PASS**, без ошибок и пропусков, **90,07 мс**. После финальной интеграции `ChatScreen` ещё раз выполнен `npm run typecheck`: **exit 0**.

Первый запуск был до появления модулей и завершился ожидаемым `ERR_MODULE_NOT_FOUND`; это проверка отсутствующей новой реализации, не воспроизведение старого пользовательского дефекта. После реализации все 10 сценариев прошли. Последующее перемещение общей проверки формата в `formats.ts` согласовано с основным агентом, чтобы политика выбора изображений не дублировалась.

Первый TypeScript-прогон выявил недопустимый `pointerEvents` у RN `Image`; свойство перенесено на окружающий `View`. После появления объявлений общего pipeline `npm run typecheck` завершился **exit 0**. Это подтверждает согласованность TypeScript-контракта, но не исполнение native pipeline.

## Что здесь не подтверждено

Не выполнялись реальные жесты, системный picker, клавиатура и установка на физических Android/iPhone. Десять unit-проверок не проверяют качество маски ML Kit/Vision или качество восстановления текстур. Наличие UI-кнопок само по себе не является подтверждением native runtime; доступность фона и необходимость подготовки модели берутся из bridge, а ошибки не превращаются в фиктивный успешный результат.

Для Android сведения о Google ML Kit показаны в блоке фона **независимо от готовности модели**. Указано, что фото и результат не передаются Google, SDK может загружать модели/обновления и отправляет метрики использования/производительности. Источник формулировки: [ML Kit Terms & Privacy, раздел Privacy](https://developers.google.com/ml-kit/terms), проверено 28 октября 2026 года. Утверждение об отсутствии всех сетевых обращений не делается. Редактор не реализует отправку исходного изображения облачному редактору.

## Независимый обзор общего пути фото

После интеграции проверены актуальные `photo/pipeline.ts`, `e2ee/attachments.ts` и Kotlin/Swift `linea-photo`. Исходники этих модулей UI-агент не изменял.

- **Путь кэша.** Native использует `<cache>/linea-photo/`; JS проверяет тот же каталог и строгое имя PNG. Сопоставлены исходники установленного Expo: Android `AppDirectoriesService.cacheDirectory` возвращает `context.cacheDir`, а стандартный iOS `AppContextConfig` использует пользовательский `cachesDirectory`. Это подтверждение конфигурации standalone-проекта, не проверка произвольного scoped Expo-контейнера.
- **Цвет и ориентация.** Android запрашивает ARGB8888/sRGB и применяет EXIF flip/rotation перед экспортом. Swift создаёт thumbnail с orientation transform и переписывает пиксели через 8-битный sRGB CGContext; Vision возвращает RGBA8/sRGB. Корректность на конкретных файлах и телефонах этим статическим обзором не доказывается.
- **Граница загрузки.** `encryptAndUpload` вызывает `preparePhotoForUpload` до чтения данных для шифрования. Для фото PNG ещё раз очищается перед `seal`; размер вложения берётся из итоговых байтов. Ошибка подготовки не включает загрузку исходника как fallback.
- **Маска и alpha.** Native ограничивает площадь маски и количество операций. Белый фон композитится с alpha, документ становится непрозрачным, увеличение интерполирует premultiplied channels. Вне маски inpainting сохраняет пиксели. Эти выводы — чтение реализации; JVM-тесты владельца native проверяют отдельные численные случаи.
- **Размер.** Оба native exporter проверяют 20 МиБ и допускают дополнительное уменьшение только при `allowDownsample=true`, с ограниченным числом попыток. JS повторно проверяет лимит и размеры PNG.

При обзоре найдены два конкретных края очистки: Swift не очищал уже записанный PNG при ошибке чтения его атрибутов; Android не проверял результат удаления слишком большого промежуточного PNG. Они переданы владельцу native и исправлены: добавлен per-attempt cleanup на Swift и отказ `DELETE_FAILED` на Android. Исправленные участки повторно прочитаны. Фактический отказ файловой системы всё равно нельзя выдавать за гарантированное удаление; startup cleanup остаётся дополнительным механизмом.

После изменения disclosure выполнен ещё один `npm run typecheck` на версии 0.4.0: **exit 0**. Независимым аудитом безопасности или проверкой физического runtime этот обзор не является.
