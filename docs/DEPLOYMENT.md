# Размещение «Линии» на .ru и .com

Конфигурация рассчитана на один Linux-сервер, два доменных имени, один процесс API и общую базу SQLite. Развёртывание в интернете ещё не выполнено: домены, сервер и доступ к DNS в этой сессии не предоставлены.

Пошаговый маршрут с телефона и отдельный серверный архив описаны в [DEPLOY_FROM_IPHONE.md](DEPLOY_FROM_IPHONE.md). Упомянутые ниже инструкции сборки мобильного клиента и отчёты тестирования входят в полный исходный комплект `linea-messenger-v0.5.1.zip`.

## Что приобрести и подготовить

1. Зарегистрировать два доступных домена, например `example.ru` и `example.com`. Доступ к DNS нужен для каждого домена. Регистратор доменов и хостинг могут быть разными компаниями.
2. Арендовать VPS/VDS с постоянным публичным IPv4, Linux, SSH-доступом и возможностью запускать Docker. Обычный тариф для PHP-сайтов не подходит, если он не позволяет запускать постоянный Node.js-процесс и WebSocket.
3. Для небольшого тестового запуска ориентир — 2 vCPU, 4 ГБ RAM, 40–60 ГБ SSD. Это исходная инженерная оценка, а не обещание конкретного числа пользователей. Расход диска зависит прежде всего от вложений; расход сети — от их отправки и скачивания. Ограничение `USER_STORAGE_MIB` задаёт квоту одного аккаунта и не заменяет контроль свободного места сервера.
4. Подготовить отдельное защищённое место для резервных копий. Копия на том же VPS не защищает от потери всего сервера.
5. Выбрать основное имя API для мобильной сборки. Второе имя будет обращаться к той же базе. Для первого выпуска рекомендуется не переключать адрес автоматически: локальные ключи клиента привязаны к адресу сервера и аккаунту. Ручной переход между доменными псевдонимами может создать новую локальную криптографическую идентичность и потребовать проверки кодов устройств.

Для передачи сервера используйте согласованный защищённый доступ. Не размещайте пароли, приватные SSH-ключи и токены DNS в исходниках, архиве приложения или публичных сообщениях.

## DNS

Пример для поддоменов API:

| Зона | Имя | Тип | Значение |
|---|---|---|---|
| example.ru | api | A | публичный IPv4 VPS |
| example.com | api | A | тот же публичный IPv4 VPS |

Если API должен открываться прямо на `example.ru` и `example.com`, создайте записи для корня зоны (`@` в большинстве панелей) и укажите эти имена в конфигурации. Два домена не требуют двух серверов или двух баз данных.

Добавляйте `AAAA` только при рабочем публичном IPv6 на этом сервере. Неверная IPv6-запись может мешать подключению и выпуску сертификата. Проверяйте оба имени с внешней сети после распространения DNS.

Основные домены можно использовать для отдельной страницы приложения и ссылок на скачивание, оставив API на `api.*`. Текущий файл Caddy не разворачивает полноценный браузерный мессенджер: на корневом пути он показывает только короткую служебную страницу. Сквозное шифрование этой версии предназначено для нативных Android/iPhone-сборок.

## Установка

Установите Docker Engine и Compose plugin по [официальной инструкции Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Конфигурация совместима с актуальным Docker Compose V2. В архиве нет приватных ключей, базы данных или пользовательских файлов.

Перенесите исходники на VPS и из корня проекта выполните:

```bash
cp deploy/.env.example deploy/.env
```

В `deploy/.env` замените `PUBLIC_HOST_RU` и `PUBLIC_HOST_COM` на **свои реальные DNS-имена**, без `https://` и путей. Не запускайте выпуск сертификатов для имён-примеров. Убедитесь, что TCP-порты 80/443 доступны снаружи; UDP 443 используется для HTTP/3. SSH разрешайте только необходимым администраторам. Прямой публичный порт API 3001 не нужен.

```bash
docker compose --env-file deploy/.env -f deploy/compose.production.yml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.production.yml up -d --build
docker compose --env-file deploy/.env -f deploy/compose.production.yml ps
docker compose --env-file deploy/.env -f deploy/compose.production.yml logs --tail=100 api caddy
```

В этой конфигурации только Caddy публикует сетевые порты. API находится во внутренней Docker-сети. Caddy передаёт реальный IP клиента, а API доверяет этому заголовку только от фиксированного адреса контейнера Caddy `172.30.58.2`. Не заменяйте список доверенных прокси на `*` или `true`. Если выбранная Docker-подсеть занята, измените согласованно подсеть, оба статических адреса и `TRUSTED_PROXIES`.

Caddy автоматически получает и продлевает HTTPS-сертификаты для обоих указанных имён и перенаправляет HTTP на HTTPS. Его данные и сертификаты находятся в постоянных Docker volumes. Условия автоматического выпуска перечислены в [официальной документации Caddy](https://caddyserver.com/docs/automatic-https). [Reverse proxy Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) поддерживает WebSocket, который нужен для новых сообщений.

Проверьте реальные имена:

```bash
curl --fail https://api.example.ru/health
curl --fail https://api.example.com/health
```

В этих командах также замените примеры своими доменами. Оба ответа должны содержать статус работающего сервера. Проверка `/health` не заменяет реальный обмен сообщениями между двумя телефонами через мобильную сеть.

## Сборка мобильного клиента

Production-сборка требует HTTPS. Пример переменных перед Android/iOS сборкой:

```bash
export APP_ENV=production
export EXPO_PUBLIC_API_URL=https://api.example.com
```

Укажите выбранный основной домен. Адрес будет установлен в приложении, и новому пользователю не понадобится вводить его вручную. Инструкции сборки находятся в `docs/BUILD.md`. Для iPhone нужны macOS/Xcode в облаке EAS либо на собственном Mac и корректная подпись приложения. Маршрут с одного iPhone описан в `tools/ios-cloud-setup/README.md` полного исходного комплекта. Наличие сервера не заменяет сборку и разрешённое распространение iOS-приложения.

Серверная HTTPS-защита и сквозное шифрование выполняют разные задачи. HTTPS защищает соединение с сервером, включая вход в аккаунт. Содержимое новых личных сообщений дополнительно шифруется на устройствах. Серверу всё ещё доступны необходимые для доставки метаданные: аккаунты, участники разговора, время, размер пакетов и IP соединения. Пароль и два слова не являются ключами расшифровки истории.

## Хранение и копии

Volume `linea-data` содержит SQLite, служебные данные аккаунтов и файлы вложений. Не выполняйте `docker compose down -v` на рабочем сервере: этот флаг удаляет постоянные volumes. Обычный `up -d --build` сохраняет их.

Для согласованной копии в этой небольшой конфигурации предусмотрен `deploy/backup.sh`. Он кратковременно останавливает API, копирует базу, WAL и файлы в одно состояние и запускает API снова. На время операции сообщения не доставляются; клиенты переподключаются после запуска. Выполняйте из каталога проекта:

```bash
bash deploy/backup.sh /var/backups/linea
```

Скрипт выводит SHA-256 архива и не удаляет старые копии. Настройте отдельную доставку зашифрованных копий на другой сервер или объектное хранилище и политику хранения. Пока это не настроено, автоматических внешних резервных копий нет. Не считайте копирование успешным процессом восстановления, пока не проверили архив на отдельном тестовом сервере.

Для восстановления сначала остановите тестовый API и извлеките архив в его пустой data volume, сохранив владельца файлов. После запуска проверьте схему, вход, чаты и доступ к вложениям. Не распаковывайте копию поверх работающей SQLite. Восстановление серверной копии не создаёт потерянные приватные ключи телефонов и не возвращает старую расшифрованную историю на новое устройство.

## Перед реальным выпуском

Проверьте HTTPS и WebSocket с обоих имён, обмен зашифрованными текстами и вложениями на двух устройствах, восстановление пароля с десятиминутным ожиданием, отказ после отзыва сессии и восстановление из резервной копии. Отдельно нужны нагрузочные измерения и независимая проверка безопасности приложения. Один сервер с SQLite подходит для контролируемого первого запуска; горизонтальное масштабирование потребует общей БД, общего файлового хранилища и доставки событий между процессами. Просто добавить второй API-контейнер к текущему локальному SQLite недостаточно.

APNS/FCM push-уведомления для полностью закрытого приложения ещё не подключены. Второй домен на том же VPS даёт другой адрес, но не защищает от отказа самого VPS. Мониторинг доступности, свободного диска, ошибок и состояния резервных копий должен быть включён при размещении.

## Обновление до 0.5.1

До первого запуска API 0.5.1 на существующих данных сделайте согласованную резервную копию. Миграция схемы 4 → 5 сохраняет конечные выдачи и добавляет бессрочную Platina. Старый сервер 0.5.0 схему 5 не откроет. Порядок выдачи по постоянному UUID и восстановления прежней версии — [PLATINA_OWNER_0.5.1.md](PLATINA_OWNER_0.5.1.md).
