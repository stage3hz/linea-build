# Линия 0.5.0: только сквозное шифрование переписки и звонков

Требование пользователя: переписки и звонки работают только со сквозным шифрованием. Для существующих личных чатов это обязательное правило кода; для ещё не реализованных групп и звонков — условие их допуска в приложение. Открытого режима и автоматического понижения защиты быть не должно.

## Реализованная защита личных чатов

- Отправка идёт через `CryptoService.encrypt` → `Api.sendEncrypted`. Неработающий нативный модуль, неизвестный ключ, ошибка шифрования или записи состояния останавливают отправку.
- Текст, имя и MIME вложения, ключ файла, миниатюра и описание медиа находятся внутри Signal payload. Сам файл шифруется на устройстве отдельным случайным ключом.
- Сервер всегда отвергает `text`/`attachmentId` в запросе отправки, в том числе вместе с `encrypted`. Режим конструктора, который включал старый открытый протокол для тестов, удалён. HTTP и WebSocket не имеют переключателя защиты.
- Исторические строки старой базы выдаются только как заглушки. Их незашифрованные вложения закрыты даже для загрузившего их участника. Исключение — файл, отдельно и сознательно опубликованный владельцем как аватар.
- Старые записи на диске не удаляются и не объявляются зашифрованными задним числом. Для ранее существовавшего открытого архива нужна отдельная согласованная миграция; текущий API закрывает его выдачу.
- Ключи идентичности закрепляются на устройстве. До первого обмена пользователи сравнивают код через доверенный канал; новые устройства и изменившиеся ключи требуют проверки.
- Восстановление пароля не выдаёт новому телефону ключи истории. Сохранившееся локальное хранилище может продолжить работу после входа; потерянные ключи сервер не восстанавливает.
- Release/preview APK принимает только HTTPS-адрес сервера; WebSocket использует WSS. Локальный HTTP возможен только в dev runtime с явным `EXPO_PUBLIC_ALLOW_LOCAL_HTTP=1`. По умолчанию Android cleartext traffic и исключения iOS ATS выключены.

Вначале воспроизведены два нарушения старого режима: открытая отправка при устаревшей опции конструктора и выдача legacy-полей сериализатором. После удаления режима обе проверки проходят. Дополнительно проверены закрытие legacy-файлов, обязательный HTTPS в release и явное разрешение локального HTTP только при разработке. Все прежние 16 серверных транспортных регрессий переведены на synthetic ciphertext fixtures без ослабления production-кода. Настоящая криптография проверяется отдельно с официальным libsignal, включая Kotlin ↔ Node и реальный HTTP API. Итоги полного прогона — `TEST_REPORT.md`.

## Граница защиты

Сервер знает участников, публичные ключи, время и размер пакетов, отметки прочтения и набор текста. Публичные профили и аватары не являются приватным содержимым переписки. E2EE не скрывает экран от самого получателя и не защищает содержимое на уже скомпрометированном телефоне.

История и криптографическое состояние хранятся в SQLCipher, ключ — в SecureStore. При просмотре расшифрованный файл временно находится в приватном кэше приложения; закрытие просмотра и следующая очистка удаляют принадлежащие приложению временные файлы. Это не обещание физического стирания всех копий во флеш-памяти.

**AI — отдельная внешняя обработка по явному согласию.** Введённый в AI-вкладке запрос получают сервер Линии и AI-провайдер: этот путь не называется E2EE-разговором между людьми. Личные чаты, контакты и ключи в запрос автоматически не добавляются. Передача переписки AI без отдельного решения пользователя не разрешена.

## Звонки: условия перед включением

**В 0.5.0 звонки не реализованы.** Нет WebRTC media path, signaling API, TURN/SFU или телефонных испытаний. Разрешения микрофона и камеры для звонков заблокированы. Эта спецификация не означает готовность звонков.

Обязательные условия следующего этапа:

1. Аудио и видео шифруются на конечных устройствах. Сеанс криптографически связан с проверенными идентичностями участников; неизвестный или подменённый ключ блокирует установление связи.
2. Прямое соединение и TURN-перенаправление не дают посреднику возможности расшифровать media. Ключи записи содержания на сервер не передаются.
3. Для конференции через SFU требуется отдельная E2EE-защита кадров поверх транспортной защиты. Само наличие HTTPS или WebRTC до SFU этого не доказывает. SFrame описывает подходящую модель; библиотека и управление ключами ещё не выбраны и не внедрены.
4. Изменение состава требует корректной смены ключей: вышедшему участнику недоступны будущие ключи. Запись, транскрипция или AI не становятся скрытыми получателями.
5. Отсутствие E2EE на любой стороне, сбой проверки целостности или смены ключа приводят к отказу/завершению звонка, без открытого запасного режима.
6. До включения необходимы проверки двух реальных телефонов: разные сети, TURN, фон/возврат, смена устройства, подмена ключей, повторы пакетов и изменение состава. В серверных журналах и хранилищах не должно быть media plaintext и секретных ключей.

Различие транспортной защиты и E2EE кадров через SFU описано в [RFC 9605, разделы 1, 5, 7 и 9](https://www.rfc-editor.org/rfc/rfc9605.html). Это направление реализации и критерии приёмки, а не внедрённый в текущую версию SFrame.

Независимый аудит безопасности и испытания Android/iPhone на физических устройствах пока не выполнены. Абсолютное обещание «никто никогда не прочитает» не даётся.
